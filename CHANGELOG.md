## Unreleased

- A buyer can submit a tool name, logo, one-line description, and https URL with a featured placement. The card is stored in `drizzle/0014_sponsorship_creatives.sql` (journal idx 12, after `0013_sponsorship_paid_at`) and stays hidden until an allowlisted admin approves the name, logo, text, and URL. Approval and rejection each append an audit row with the actor, time, decision, and reason. The review table rejects later updates and deletes. A rejected card tells the admin that refunds are done in the Stripe dashboard; this change does not call Stripe to refund. An approved card is pinned inside the Sponsored box at the top of that /best page, with `rel="sponsored nofollow"`, and it is not added to the editorial ranking. `/sponsor` says the card is reviewed before it goes live, rejected orders are refunded, and an approved card is published with a Sponsored label.
- A sponsored placement’s week or month starts at `paid_at`, the first time the row became paid. Later webhook updates do not move that clock. `paid_at` and `refunded_at` land in `drizzle/0013_sponsorship_paid_at.sql` (journal idx 11, after `0012_result_rate_windows`). This SQLite build rejects `ADD COLUMN IF NOT EXISTS`, so `adoptSponsorshipSchema` adds a missing column and backfills `paid_at` from `updated_at` for rows that are already paid. Nothing is dropped. `charge.refunded` and a succeeded `refund.*` event set `refunded_at` once, matched on the payment intent, and that row stops showing. The status check stays `pending`, `paid`, or `failed`. The disclosure heading and the links that pointed at it, including the one in the Sponsored box, say Disclosures. A sponsorship read that throws on `/best` logs the error name only and renders no box. The box has its own Sponsored heading and a top border so it is not read as the tool above it. Buyer company names lose bidi and control characters before checkout and again before render. `/sponsor` says the company name is published with a Sponsored label.
- A /best guide shows a Sponsored label when a paid featured placement for that task is still inside its week or month. Pending, failed, expired, and newsletter sponsorships do not. The disclosure page says BestBotFor accepts those paid placements and newsletter sponsorships, and that both are labeled Sponsored.

Loopback http is accepted only when the request host is itself loopback and the environment is not production. The return URLs are part of the Checkout idempotency key. Other hosts are ignored. The sponsorship tables land in `drizzle/0009_sponsorships.sql`, after main’s `0008_ratings_v23.sql`. - Rate-limit bucket ids are an HMAC-SHA256 under an HKDF-SHA256 subkey of `RATE_LIMIT_HMAC_SECRET`. The HKDF info is `bestbotfor/rate-limit/v1`, with the same salt as the click-log subkey `bestbotfor/click-ip/v1`. The raw secret is not the HMAC key. Click-log hashes stay on `bestbotfor/click-ip/v1`. Counters already stored under the raw secret reset once when this deploys. Those windows last at most 24 hours.
- A path with a malformed percent-escape, such as `/%E0%A4%A` or `/admin/%E0%A4%A`, returns plain text 400 with `Cache-Control: no-store` and `X-Robots-Tag: noindex, nofollow`. Next decodes `/:path*` header params before the proxy runs, and that throw was a 500. The proxy rejects the raw path when it runs. `scripts/serve.ts` and a `vercel.json` route reject it before Next decodes. A valid encoding such as `/tools/%63hatgpt` still reaches that tool page.
- `/admin` is limited to a Clerk user whose `publicMetadata.role` is `admin` and whose id is in `ADMIN_CLERK_USER_IDS`. Signed-out, normal, and role-only users get a 404. - Review IP HMAC secrets are checked by one validator at build and at server boot. `REVIEW_IP_HMAC_SECRET` is required when `VERCEL_ENV=production` and when `USER_RATINGS=on`, must be at least 32 bytes, and has no fallback key. `REVIEW_IP_HMAC_KEY_ID` is required with it and must match `^k[1-9][0-9]{0,3}$`. An optional `REVIEW_IP_HMAC_SECRET_PREVIOUS` must be at least 32 bytes and needs `REVIEW_IP_HMAC_KEY_ID_PREVIOUS` in that format and different from the current id. A previous id without a previous secret is refused. The review secret must not equal `RATE_LIMIT_HMAC_SECRET` or the previous review secret; the check compares SHA-256 digests with `timingSafeEqual`. `RATE_LIMIT_HMAC_SECRET` must be at least 32 bytes in production. Preview still uses the HKDF fallback when that secret is unset. `K_ip` and `K_net` derive HKDF-SHA256 subkeys (`bestbotfor/review-ip/v1`, `bestbotfor/review-net/v1`) for a later review writer. `BBF_E2E_HOOKS=1` fails the build when `VERCEL=1` or `VERCEL_ENV=production`. `NODE_ENV=production` does not refuse the hooks, because `next build` always sets it. Key ids are matched exactly, so leading or trailing whitespace is refused. Errors name the variable and the rule only.

- A `RATE_LIMIT_HMAC_SECRET` shorter than 16 characters is not used as the HMAC key. The process derives a 32-byte key with HKDF-SHA256 from another server secret of at least 16 characters, and logs a warning that names the source variable. When no candidate is long enough, it keeps one process-local key and warns about that instead. The secret and the derived key are not logged.
